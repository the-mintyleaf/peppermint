# MintFlow Work Module — Architecture, Requirements, Dynamic Hierarchy Workflow, and Integration Contract

**Document status:** Implementation-grade architecture and requirements specification  
**Module owner:** `work`  
**Contract version:** `1.0.0`  
**Snapshot date:** 2026-07-17  
**Target stack:** Django 5.1.9, Django REST Framework, PostgreSQL  
**Deployment posture:** Local-first, privacy-first, audit-first  
**Intended reader:** Backend architect, Claude Code, implementation reviewers, security reviewers, QA engineers

---

## 1. Document purpose

This document defines the `work` module for MintFlow. It is intended to be sufficiently explicit that an AI coding agent cannot safely invent its own domain rules, static approval chains, hidden authorization logic, or undocumented schema.

This is a final implementation requirement, not a brainstorming note. It should be treated as a government-grade, audit-first, least-privilege, need-to-know specification aligned with established institutional security practice: immutable history, explicit lifecycle transitions, anti-enumeration, document provenance, separation of duties, and no hidden state.

The module is the operational heart of MintFlow. It must track:

- what objective must be achieved;
- who created it;
- which organization and organizational unit are responsible;
- which actor is currently accountable;
- which actors execute tasks and subtasks;
- what actions were performed;
- what evidence supports those actions;
- where delay or blockage occurred;
- which hierarchy path controlled assignment, response, review, and escalation;
- who reviewed the result;
- how the work concluded;
- what was communicated to internal and external stakeholders.

The governing principle is:

> At every point in time, MintFlow must be able to explain who was accountable, what was expected, what happened, what evidence supports it, where it was delayed, who reviewed it, how it concluded, and under what authority each action occurred.

## 2. Authoritative existing project context

The current backend already contains these governance modules:

| Existing module | Authoritative responsibility |
|---|---|
| `authenticate` | Actor identity, authentication eligibility, sessions, MFA, service accounts, security state |
| `organization` | Organizations, units, closure-table hierarchy, positions, position assignments, memberships, reporting lines, delegations, structural history |
| `permissions` | Roles, role bindings, direct grants, direct denials, and permission decision evaluation at global, organization, and organization-unit scope |
| `core.policy_engine` | Registry of applications, models, endpoints, permission keys, categories, dependencies, versions, and policy changelogs |
| `core` | Shared API envelope, exception formatting, logging, request ID, pagination, authentication defaults, health/readiness infrastructure |

The `work` module must integrate with these modules. It must not duplicate their source-of-truth data or build a second identity, organization, hierarchy, authorization, or policy system.

The repository does **not** currently contain final standalone `cases`, `events`, `notifications`, `documents`, `audit`, or `evaluation` applications. This specification defines clean integration boundaries for them without silently implementing those domains inside `work`.

If the foundational `events` app is introduced in this program, it must remain domain-neutral and project-wide. It should own only generic append-only event infrastructure, not work semantics. `work` remains the source of truth for work state and work history, while `events` receives durable event envelopes for institutional memory, search, analytics, projection, and audit consumption. The initial architecture already places a foundational event ledger before `work`; if implemented now, it must be the first controlled prerequisite, not a replacement for work history.

## 3. Definition of work

### 3.1 Formal definition

> A Work Item is an auditable organizational objective assigned to one accountable actor, executed through tasks and subtasks, supported by activity records and evidence, governed by dynamic organizational hierarchy, and resolved through a controlled closure process.

### 3.2 Work aggregate

A work item is not merely a row with `title`, `assignee`, and `status`. It is an aggregate containing:

```text
Objective
├── Accountable ownership
├── Responsible organization and unit
├── Tasks and subtasks
├── Execution assignments
├── Participants
├── Hierarchy resolutions
├── Activity records
├── Evidence references
├── Reviews and review rounds
├── Status transitions
├── Closure decision
├── Internal notification events
└── External stakeholders
```

### 3.3 High-level lifecycle

```text
Start → Actions → Closure
```

Expanded:

```text
Creation → Assignment/Acceptance → Execution → Review → Closure → Archive
```

## 4. Module ownership boundary

### 4.1 The `work` module owns

- work objectives and descriptive details;
- current accountable owner and ownership history;
- responsible organization and organizational unit references;
- task and subtask hierarchy;
- execution assignments and assignment responses;
- work participants;
- dynamic hierarchy resolution snapshots for work actions;
- routing and cross-unit handoff records;
- append-only work activity records;
- work-specific evidence associations;
- immutable document attachment provenance and document-version references used by work;
- work and task status transitions;
- review requests, rounds, decisions, and comments;
- work closure outcomes;
- archival and restoration state;
- external concerned-party relationships to work;
- transactional outbox records for downstream notifications/events;
- neutral operational metrics and durations derived from work history.

### 4.2 The `work` module does not own

- passwords, authentication, sessions, MFA, or actor security state;
- organization/unit creation or hierarchy maintenance;
- positions, reporting-line definition, memberships, or delegation definition;
- role/grant/deny creation or general permission evaluation;
- policy registry internals;
- physical file-lake design or generalized document storage;
- generalized notification inbox/delivery preferences;
- universal event ledger;
- formal audit findings;
- employee or department performance scoring;
- case lifecycle;
- generalized configurable workflow templates;
- AI-generated autonomous decisions.

### 4.3 Cross-app coupling rule

- Foreign keys to authoritative identity and organization models are permitted when required.
- Business reads from another app must use that app's documented public selectors.
- Business mutations in another app must use that app's documented public services.
- The implementation must not import another app's internal service helpers, private utilities, serializers, or view logic.
- Actual existing selector/service names must be inspected in the repository. Claude must not invent names and claim they already exist.

## 5. Non-negotiable domain invariants

### INV-001 — Every active work item has one accountable actor

Every non-archived work item must have exactly one current accountable owner.

- If no owner is selected at creation, the creator becomes owner.
- If another actor is selected, accountability transfers only after the assignment or handover is accepted according to the rules in this document.
- No active work may become ownerless.

### INV-002 — Every work item has organizational scope

Every work item must reference:

- one organization;
- one responsible organizational unit;
- one accountable actor.

### INV-003 — Creator is immutable

`created_by` and `created_at` never change. Ownership transfer never rewrites the creator.

### INV-004 — Ownership cannot be changed by direct field update

Changing current accountable ownership must use the ownership-transfer service. Direct serializer updates to `current_owner` are forbidden.

### INV-005 — Ownership transfer requires explicit acceptance

The current owner remains accountable until the proposed owner accepts. Rejection, expiry, or cancellation leaves current ownership unchanged.

### INV-006 — Work and tasks are never hard deleted

Delete behavior is archive behavior. Historical records remain queryable by authorized users.

### INV-007 — Meaningful mutations create append-only history

Every assignment, acceptance, rejection, routing, transfer, start, block, unblock, review submission, review decision, completion, closure, reopening, archive, restore, evidence verification, and correction must create a historical record.

### INV-008 — Status cannot be arbitrarily patched

Statuses change only through named service commands with transition validation. Generic `PATCH status=...` is forbidden.

### INV-009 — Hierarchy is dynamically resolved

No department name, actor ID, position ID, or approval chain may be hard-coded into work logic. Assignment response, review, escalation, and visibility must resolve from the effective organization structure.

### INV-010 — Historical hierarchy decisions cannot be rewritten

Every hierarchy-driven decision stores an immutable resolution snapshot. Later changes to units, heads, reporting lines, positions, or delegations must not alter the historical explanation of an earlier decision.

### INV-011 — Future hierarchy actions use current effective structure

Visibility, future review resolution, escalation, and newly issued routing decisions use the current effective hierarchy at the time of the action.

### INV-012 — Hierarchy changes do not silently transfer ownership

Moving a unit, changing a unit head, or changing an actor's supervisor does not automatically rewrite current work ownership. Ownership changes only through explicit transfer/reassignment rules, except controlled recovery when the owner is no longer eligible.

### INV-013 — Activity and evidence history is correction-based

Submitted accountability entries are not silently edited. Corrections create a new record referencing the incorrect or superseded record.

### INV-014 — Review-required work cannot self-complete

When review is required, execution completion produces a review submission, not final completion. Final completion depends on an authorized review decision.

### INV-015 — Closure and successful completion are different concepts

A work item may close as completed, partially completed, not completed, cancelled, duplicate, superseded, out of scope, or withdrawn.

### INV-016 — Relationship does not replace permission

Being creator, owner, assignee, reviewer, participant, unit head, or ancestor head may establish resource relevance or visibility, but the actor must still possess the required permission key through the `permissions` module.

### INV-017 — Permission does not automatically expose every row

Having a broad action permission does not automatically permit reading every work item. Work-specific visibility, organization scope, hierarchy relationship, and sensitivity rules must also pass.

### INV-018 — Work records facts; evaluation interprets them

The work module may calculate durations and counts. It must not label an actor or department good, poor, efficient, inefficient, or underperforming.

## 6. Dynamic hierarchy-driven workflow

This is a foundational requirement.

The work lifecycle is stable, but the people and units responsible for assignment, response, review, escalation, and visibility are determined dynamically from the organization structure.

### 6.1 Authoritative organization inputs

The hierarchy resolver must use effective records from the `organization` module, including where applicable:

- organization membership;
- organization-unit membership;
- active position assignment;
- explicit reporting line;
- unit head position and current assignee;
- parent/ancestor units from the closure table;
- root unit or organization-level head;
- active delegation;
- membership, assignment, reporting-line, and delegation effective dates;
- unit and organization active state.

### 6.2 Resolution precedence

For a hierarchy-dependent target such as reviewer, escalation recipient, response recipient, or supervisor, use this precedence:

1. An explicitly assigned authorized target for the current action, when the action allows explicit selection.
2. The active explicit reporting-line supervisor of the responsible actor or position.
3. The active head of the actor's responsible unit.
4. The active head of the nearest ancestor unit.
5. Continue upward through ancestor units.
6. Resolve the root-unit or organization head.
7. Apply an active eligible delegation when the resolved authority has delegated the relevant action/scope.
8. If no eligible target exists, block the action with `WORK_HIERARCHY_TARGET_UNRESOLVED`; never guess.

### 6.3 Effective-time rule

Each hierarchy lookup must use an explicit `effective_at` timestamp.

- For a new action, `effective_at` is normally the current transaction time.
- For reconstructing history, use the timestamp stored in the resolution snapshot.
- Never use today's hierarchy to explain an action that occurred under an older hierarchy.

### 6.4 Hierarchy resolution snapshot

Every hierarchy-driven action must store:

- organization ID;
- source actor ID;
- source unit ID;
- source position ID when applicable;
- resolved target actor ID;
- resolved target unit ID;
- resolved target position ID when applicable;
- ordered unit ancestry path;
- ordered reporting/authority path where available;
- resolution strategy used;
- delegation ID when used;
- effective timestamp;
- reason for resolution;
- action type;
- source work/task/assignment/review identifier;
- structure/history identifiers when exposed by the organization module.

### 6.5 Hierarchy-change behavior

| Situation | Required behavior |
|---|---|
| Unit moves under another parent | Past snapshots remain unchanged; future visibility/escalation uses new ancestry |
| Unit head changes | Existing owner remains; future unit-head visibility and new hierarchy actions use new head |
| Actor's supervisor changes | Past review/routing records remain; future supervisor resolution uses new reporting line |
| Owner changes unit but remains eligible | Ownership remains unless business rules require transfer; visibility is recomputed from current responsible work unit and explicit participation |
| Owner becomes inactive, leaves organization, or loses eligibility | Work enters reassignment-required state; authorized hierarchy resolves a replacement; previous owner remains in history |
| Delegation begins | New eligible actions may resolve to delegate; existing historical targets remain unchanged |
| Delegation ends | Future actions revert to normal authority chain |
| Organization structure cannot resolve a head | Action is blocked and surfaced to authorized administrators; no silent fallback to arbitrary staff |

### 6.6 Assignment response path

The response path must not be a static “send to department head” rule.

For a task or work response:

1. Prefer the actor who issued the active assignment when that actor remains active and authorized within the relevant scope.
2. If the assignment issuer is no longer eligible, dynamically resolve the nearest eligible superior through the current hierarchy.
3. For a cross-unit task, return operational results to the accountable work owner while preserving visibility for the assignee's unit head and ancestors.
4. For a work-level completion submission, resolve the reviewer using the owner's current effective hierarchy unless an explicit authorized reviewer was established.
5. A return as “not completed” must include a reason, supporting activity/evidence, and the hierarchy resolution used.

### 6.7 Unit-targeted routing

When work is routed to an organizational unit rather than a named actor:

- the unit becomes the responsible routing target;
- the system resolves the unit's active dispatcher position if such a documented concept exists in `organization`;
- otherwise it resolves the active unit head;
- otherwise it walks to the nearest ancestor head;
- the resolved actor receives a pending assignment or routing request;
- the work remains owned by the previous owner until acceptance;
- a unit queue view must expose pending routed work to authorized unit leadership;
- routing loops must be detected.

### 6.8 Routing loop detection

The system must detect repeated routing paths such as:

```text
Unit A → Unit B → Unit A
```

Required safeguards:

- store every routing hop;
- reject an identical immediate reverse route unless an override reason and permission exist;
- detect repeated units within the active route chain;
- after a configurable maximum hop count, escalate to the nearest common ancestor head;
- do not hard-code the hop limit in views; define it in module configuration with a documented default.

### 6.9 Dynamic hierarchy flowchart

```mermaid
flowchart TD
    A[Hierarchy-dependent work action requested] --> B[Authenticate actor]
    B --> C[Check policy permission at org/unit scope]
    C -->|Denied| X[Return stable authorization error]
    C -->|Allowed| D[Load effective organization context]
    D --> E{Explicit eligible target exists?}
    E -->|Yes| J[Select explicit target]
    E -->|No| F{Active reporting-line supervisor?}
    F -->|Yes| J
    F -->|No| G{Active unit head?}
    G -->|Yes| J
    G -->|No| H[Walk ancestor units]
    H --> I{Eligible ancestor/root head found?}
    I -->|No| Y[Block: hierarchy target unresolved]
    I -->|Yes| J
    J --> K{Eligible active delegation applies?}
    K -->|Yes| L[Resolve delegate]
    K -->|No| M[Keep resolved authority]
    L --> N[Create immutable hierarchy snapshot]
    M --> N
    N --> O[Validate work lifecycle preconditions]
    O -->|Invalid| Z[Return lifecycle error; no mutation]
    O -->|Valid| P[Execute transactional work action]
    P --> Q[Write transition/activity/outbox records]
```

## 7. Actor roles inside work

These roles are work-domain relationships. They do not replace permission roles.

| Work relationship | Meaning |
|---|---|
| Creator | Immutable actor who created the work |
| Accountable owner | Single actor ultimately responsible for closure |
| Task assignee | Actor responsible for executing a task/subtask |
| Assignment issuer | Actor who issued a current assignment |
| Contributor | Actor permitted to add scoped activity/evidence |
| Reviewer | Actor responsible for a review decision |
| Watcher/observer | Actor permitted to receive updates and read within defined visibility |
| Responsible unit | Organizational unit institutionally accountable for the work |
| Task responsible unit | Unit responsible for a particular task, possibly different from work unit |
| External stakeholder | Person or institution outside internal actor scope linked for approved communication |

Rules:

- One work item has one current accountable owner.
- Tasks may have different assignees and responsible units.
- A reviewer cannot approve a submission they authored unless an explicit self-review rule and permission exists. Default: self-review forbidden.
- A unit head's visibility is derived from hierarchy, not stored as a permanent participant row for every work item.

## 8. Work lifecycle state machine

### 8.1 Work statuses

Use lowercase `TextChoices` values:

```text
assignment_pending
accepted
in_progress
blocked
review_pending
changes_requested
closure_pending
closed
archived
```

### 8.2 Initial status

- Creator remains owner: initial status is `accepted`.
- Another actor is proposed as owner: initial status is `assignment_pending`, while the creator remains accountable until acceptance.
- A unit is targeted: initial status is `assignment_pending`, and the creator remains accountable until a resolved unit recipient accepts.

### 8.3 Allowed work transitions

| From | To | Command | Core requirements |
|---|---|---|---|
| `assignment_pending` | `accepted` | accept assignment/handover | recipient eligible and authorized |
| `assignment_pending` | `accepted` | cancel proposed assignment and retain creator | creator/authorized manager; history preserved |
| `accepted` | `in_progress` | start work | owner eligible |
| `in_progress` | `blocked` | report blocker | blocker type and reason required |
| `blocked` | `in_progress` | resolve blocker | resolution note required |
| `in_progress` | `review_pending` | submit for review | required tasks/evidence satisfied |
| `review_pending` | `changes_requested` | request changes | reviewer decision and comments required |
| `changes_requested` | `in_progress` | resume changes | owner/assignee acknowledges request |
| `review_pending` | `closure_pending` | approve review | authorized reviewer |
| `in_progress` | `closure_pending` | submit closure without review | only when review is not required |
| `closure_pending` | `closed` | close work | authorized closer; closure outcome required |
| `closed` | `in_progress` | reopen work | separate permission and reason required |
| any non-archived status | `archived` | archive | separate permission and archive reason |
| `archived` | prior safe status | restore | separate permission; restoration record required |

Direct transition from `in_progress` to `closed` is forbidden.

### 8.4 Closure outcomes

```text
completed
partially_completed
not_completed
cancelled
duplicate
superseded
out_of_scope
withdrawn
```

Mandatory rules:

- `completed`: completion summary and supporting evidence/activity required.
- `partially_completed`: completed scope, unresolved scope, and reason required.
- `not_completed`: reason, accountability report, and unresolved task summary required.
- `cancelled`: cancellation authority and reason required.
- `duplicate`: canonical work reference required.
- `superseded`: replacement work reference required.
- `out_of_scope`: routing history and scope explanation required.
- `withdrawn`: withdrawing authority and reason required.

### 8.5 Work lifecycle flowchart

```mermaid
stateDiagram-v2
    [*] --> accepted: creator is owner
    [*] --> assignment_pending: another owner/unit proposed
    assignment_pending --> accepted: accepted
    assignment_pending --> accepted: proposal cancelled; creator retained
    accepted --> in_progress: start
    in_progress --> blocked: blocker reported
    blocked --> in_progress: blocker resolved
    in_progress --> review_pending: submit for review
    review_pending --> changes_requested: changes requested
    changes_requested --> in_progress: changes resumed
    review_pending --> closure_pending: approved
    in_progress --> closure_pending: review not required
    closure_pending --> closed: closure authorized
    closed --> in_progress: reopened
    accepted --> archived: archive
    in_progress --> archived: archive
    blocked --> archived: archive
    review_pending --> archived: archive
    closure_pending --> archived: archive
    closed --> archived: archive
    archived --> accepted: restore to safe state
    archived --> in_progress: restore to prior active state
```

## 9. Task and subtask model

### 9.1 Structure

Use one `WorkTask` model with a nullable self-referencing `parent_task`.

- `parent_task = NULL`: top-level task.
- `parent_task != NULL`: subtask.
- Do not create separate `Task` and `SubTask` tables.

### 9.2 Structural rules

- A parent and child must belong to the same work item.
- A task cannot be its own ancestor.
- Circular task ancestry is forbidden.
- Task ordering must be stable within the same parent.
- Task depth must be validated through a configurable maximum. Recommended initial operational maximum: 5 levels.
- Deleting a task means cancel/archive according to task lifecycle; no hard delete after any activity or assignment exists.

### 9.3 Task statuses

```text
not_started
assignment_pending
accepted
in_progress
blocked
review_pending
changes_requested
completed
returned_uncompleted
cancelled
archived
```

### 9.4 Task completion rules

- A task may be completed only by an eligible current assignee or authorized hierarchy actor.
- If review is required, the assignee submits for review; the reviewer completes approval.
- If the assignee cannot complete it, use `return_uncompleted_task()` with reason, report, evidence, and hierarchy response resolution.
- `returned_uncompleted` is not silently reassigned. The work owner or resolved hierarchy actor must decide whether to revise, reassign, cancel, or close the task.
- Parent completion may require all mandatory child tasks to be completed or explicitly waived by an authorized actor with recorded reason.

### 9.5 Dependencies

A task may depend on another task in the same work item.

Dependency types:

```text
finish_to_start
start_to_start
informational
external_blocker
```

- Circular blocking dependencies are forbidden.
- A blocked dependency must contribute to blocked-duration metrics.
- Cross-work dependencies are deferred until a `cases` or generalized workflow layer defines their contract.

## 10. Assignment, acceptance, handover, and routing

### 10.1 Assignment categories

```text
accountable_owner
executor
reviewer
contributor
observer
```

### 10.2 Assignment target

An assignment may target:

- a specific actor;
- an organization unit requiring dynamic recipient resolution;
- a position, only if the organization module exposes a stable documented position-target contract.

### 10.3 Assignment statuses

```text
pending
accepted
rejected_out_of_scope
clarification_requested
cancelled
expired
revoked
ended
```

### 10.4 Assignment response

The recipient may:

- accept;
- reject as out of scope;
- request clarification;
- recommend a unit or actor for routing.

Rejection requires:

- reason;
- optional recommended unit;
- optional recommended actor;
- comments/evidence where applicable;
- hierarchy snapshot;
- timestamp.

Rejection does not automatically transfer accountability.

### 10.5 Ownership transfer

Ownership transfer is a specialized handover:

```text
requested → accepted | rejected | cancelled | expired
```

Required fields:

- current owner;
- proposed owner;
- current responsible unit;
- proposed responsible unit when changing;
- initiated by;
- reason;
- requested at;
- expires at when used;
- accepted/rejected by;
- decision remarks;
- hierarchy snapshot;
- effective at.

Atomic acceptance must:

1. verify current ownership has not changed;
2. verify recipient eligibility;
3. re-check permission and scope;
4. close the previous owner assignment;
5. set the new current owner;
6. update responsible unit only when explicitly approved;
7. create transition/history records;
8. create outbox events;
9. increment the aggregate version.

### 10.6 Ineligible owner recovery

When an owner becomes inactive, leaves the organization, or loses required membership:

- do not erase ownership history;
- mark the work `reassignment_required` through a derived flag or integrity state, not an undocumented status;
- prevent actions that require an eligible owner;
- notify authorized hierarchy actors through outbox;
- resolve a replacement through current hierarchy;
- require an explicit reassignment service action;
- record previous and new authority context.

### 10.7 Cross-unit routing flow

```mermaid
flowchart TD
    A[Assignee determines work/task is outside scope] --> B[Submit route recommendation with reason]
    B --> C[Check actor permission and active assignment]
    C --> D[Resolve target unit recipient dynamically]
    D -->|No target| X[Block and escalate: hierarchy unresolved]
    D --> E[Detect route loop and hop limit]
    E -->|Loop/limit| F[Resolve nearest common ancestor authority]
    E -->|Safe| G[Create pending routing request]
    F --> G
    G --> H[Notify resolved recipient/unit queue through outbox]
    H --> I{Recipient decision}
    I -->|Accept| J[Transfer task or ownership atomically]
    I -->|Reject| K[Record rejection and preserve current accountability]
    I -->|Clarification| L[Return request to current owner/issuer]
    J --> M[Create hierarchy snapshot and transition history]
```

## 11. Activity and accountability log

### 11.1 Purpose

The activity log answers:

- what did the actor do;
- when did they do it;
- for which work/task;
- how long was the work actively held;
- how long the actor actively worked on it;
- what result or decision was produced;
- which evidence supports it;
- which document versions were attached, consulted, or detached during the action;
- which organizational context applied.

### 11.2 Activity types

```text
progress_update
work_performed
decision
communication
meeting
research
field_activity
document_prepared
information_requested
information_received
blocker_reported
dependency_resolved
submission
review_response
correction
system_activity
```

### 11.3 Required activity fields

- work item;
- optional task;
- actor;
- actor organization/unit/position context snapshot;
- activity type;
- description;
- occurred/started timestamp;
- optional ended timestamp;
- optional explicit duration seconds when the session is known precisely;
- recorded timestamp;
- source type (`human`, `system`, `ai_draft`);
- visibility classification;
- optional evidence links;
- optional document attachment links;
- optional correction-of reference;
- immutable submission state.

### 11.4 Immutability

After submission:

- ordinary update is forbidden;
- factual correction creates a new activity entry referencing the original;
- the original remains visible to authorized auditors;
- a correction must state why the original was wrong;
- administrative redaction, if ever required, must be a separate future legal/compliance process, not generic update/delete.

### 11.5 Time accounting

The system must distinguish:

- created time;
- assignment waiting time;
- acceptance time;
- time to first action;
- active execution time;
- blocked time;
- external waiting time;
- review waiting time;
- change-request rework time;
- closure waiting time.

Do not infer “active labor hours” solely from elapsed wall-clock time. Activity timestamps provide evidence; final labor-time analytics require explicit future evaluation rules.

### 11.6 Activity/session rule

If the module needs to know who worked on something and for how long, it must rely on explicit activity entries with actor, start time, end time, and duration, not on inferred page views or hidden background edits. Passive visibility events are not work sessions.

## 12. Work data, evidence, and files

### 12.1 Separation of concepts

**Work data** is operational information used to execute work.  
**Evidence** is information or an artifact submitted to support accountability, review, or closure.

### 12.2 Evidence types

```text
text_statement
document_reference
image_reference
external_reference
structured_payload
generated_output
approval_record
communication_record
```

### 12.3 Evidence lifecycle

```text
submitted
pending_verification
verified
rejected
superseded
invalid
```

Verification means the evidence is accepted as a valid submission for the stated purpose. It does not by itself approve the work.

### 12.4 Evidence fields

- work item;
- optional task;
- optional activity;
- submitted by;
- submitted at;
- evidence type;
- title/description;
- purpose;
- text or structured payload when applicable;
- external/source reference when applicable;
- document/file reference when available;
- version number;
- verification status;
- verified/rejected by;
- verified/rejected at;
- verification remarks;
- sensitivity/visibility;
- supersedes reference;
- checksum and MIME metadata must be owned by the future document/file service, not duplicated casually.

### 12.5 File integration gate

The current repository has no standalone `documents` app. Therefore:

- `work` must not implement uncontrolled raw file paths or ad hoc file-lake logic;
- text and structured evidence may be implemented directly;
- file-backed evidence must use a documented document/file integration contract;
- before file upload endpoints are enabled, a minimal local document service must own upload validation, MIME checks, size limits, checksum, storage path, retention, and access metadata;
- Claude must not silently create a second file-storage architecture inside `work`.

### 12.6 Document accountability ledger

Every time a document is attached to, detached from, or referenced by a work item, task, activity, evidence item, review round, or closure record, the system must create a history-preserving attachment ledger row.

The attachment ledger must answer:

- which work item the document was associated with;
- which document reference and document-version reference were used;
- who attached or detached it;
- when the attachment state changed;
- why the document was attached or detached;
- what attachment role it served;
- what visibility class applied at that time;
- whether it was a primary supporting document or a supplementary one;
- what checksum, MIME type, size, and source-service snapshot were observed at the time of association.

Attachment records are provenance records. They are not file storage.

### 12.7 Government-grade document security minimums

The future document service must enforce, at minimum:

- authenticated and authorized upload/download;
- document-version immutability;
- encryption at rest;
- checksum verification on ingest and on retrieval;
- MIME and content-type validation;
- malware scanning before release;
- document-level access control and audit logging;
- retention and legal-hold support;
- redaction or restricted-view support when required by policy;
- no raw filesystem paths exposed to work or clients;
- no direct storage-engine assumptions inside work;
- no document deletion that erases accountability history.

If a document is later revoked, deleted from the live store, or superseded, the work attachment ledger must still preserve the historical link and the security-relevant snapshot metadata.

## 13. Review and re-review workflow

### 13.1 Review scope

A review may target:

- the entire work item;
- a task;
- a subtask;
- a specific evidence package;
- a stable submission snapshot.

### 13.2 Review target resolution

Default review target:

1. explicit authorized reviewer, if assigned;
2. current assignment issuer, if still authorized and structurally appropriate;
3. active reporting-line supervisor;
4. current unit head;
5. nearest eligible ancestor head;
6. root/organization authority;
7. delegated authority when eligible.

### 13.3 Review decisions

```text
approved
approved_with_remarks
changes_requested
rejected
returned_without_review
```

### 13.4 Stable review snapshot

Each review round must freeze references to:

- work/task version;
- included activity entries;
- included evidence versions;
- included document attachment references and document-version identifiers;
- included child-task states;
- submission summary;
- requester;
- reviewer;
- hierarchy resolution snapshot.

The underlying work may continue only according to lifecycle rules. A reviewer must always know exactly what version was reviewed.

### 13.5 Review rounds

- First submission creates round 1.
- `changes_requested` returns the target to execution.
- Re-submission creates a new immutable round.
- Old rounds and comments remain unchanged.
- Approval applies only to the reviewed snapshot/version.
- Material changes after approval invalidate approval when configured by the service rules and require re-review.

### 13.6 Review flowchart

```mermaid
flowchart TD
    A[Assignee/owner prepares submission] --> B[Validate required tasks, activity, and evidence]
    B -->|Invalid| X[Return validation errors]
    B -->|Valid| C[Resolve reviewer from current hierarchy]
    C --> D[Create immutable review snapshot and round]
    D --> E[Status: review_pending]
    E --> F{Reviewer decision}
    F -->|Changes requested| G[Record decision and required changes]
    G --> H[Status: changes_requested]
    H --> I[Assignee resumes work]
    I --> A
    F -->|Approved| J[Record approval against snapshot]
    J --> K[Status: closure_pending or task completed]
    F -->|Rejected| L[Record rejection; hierarchy action required]
    F -->|Returned without review| M[Record procedural reason; resolve next reviewer]
```

## 14. Visibility and resource authorization

The current permissions application evaluates permissions at global, organization, and organization-unit scope. It does not yet provide generalized resource-instance grants. Therefore, access to work must be a two-stage decision.

### 14.1 Two-stage authorization

**Stage 1 — Action authority**  
Ask the `permissions` module whether the actor possesses the policy permission key at the relevant organization/unit scope.

**Stage 2 — Resource visibility and lifecycle authority**  
The `work` module verifies that the particular work item is visible/actionable based on ownership, assignment, participation, hierarchy, sensitivity, and lifecycle.

Both stages must pass.

### 14.2 Default visibility relationships

Subject to permission and sensitivity rules, visibility may be established by:

- creator relationship;
- current accountable ownership;
- current task assignment;
- active contributor/reviewer/observer participation;
- responsible-unit leadership;
- ancestor-unit leadership up to the highest eligible head;
- explicit auditor or administrator permission;
- approved explicit access relationship in a future row-level permissions phase.

### 14.3 Visibility modes

```text
organizational
participants_only
restricted
confidential
explicit
```

| Mode | Behavior |
|---|---|
| `organizational` | Eligible participants, responsible-unit heads, and ancestor heads may access according to permission scope |
| `participants_only` | Direct participants plus specifically authorized hierarchy/audit actors |
| `restricted` | Requires relationship plus elevated restricted-work permission |
| `confidential` | Requires confidential-work permission and need-to-know relationship; hierarchy alone is insufficient |
| `explicit` | Requires future explicit resource-access contract; not to be improvised in phase 1 |

### 14.4 Data-level visibility

Evidence and activity may be more restrictive than the parent work item.

- Parent work access does not automatically expose every confidential attachment or note.
- Each activity/evidence item stores visibility classification.
- A response serializer must filter nested records through a visibility selector; never serialize all related objects and filter afterward in Python.

Document attachments follow the same rule:

- a document attachment may be visible only to a narrower set than the parent work item;
- the attachment record must carry its own visibility classification and document-service reference;
- a caller with work access does not automatically get document download access;
- the document service remains the final authority on raw file retrieval.

### 14.5 Authorization algorithm

```mermaid
flowchart TD
    A[Request work action] --> B[Authenticate subject]
    B --> C[Resolve organization and unit context]
    C --> D[Permissions app evaluates policy key]
    D -->|Denied| X[403 stable permission error]
    D -->|Allowed| E[Load resource through visibility-aware selector]
    E -->|Not visible| Y[404 or 403 according to documented anti-enumeration rule]
    E -->|Visible| F[Check sensitivity requirements]
    F -->|Failed| Z[403 sensitivity error]
    F -->|Passed| G[Check relationship/hierarchy authority]
    G -->|Failed| W[403 resource authority error]
    G -->|Passed| H[Check lifecycle preconditions]
    H -->|Failed| V[409 lifecycle conflict]
    H -->|Passed| I[Execute service transaction]
```

### 14.6 Anti-enumeration rule

For work details not visible to the caller, use one consistent documented behavior. Recommended default: return the same not-found response used for an unknown UUID, unless the caller has a specific audit/debug permission that permits visibility into denial reasons.

## 16. Notification design

### 16.1 Boundary

The work app determines that a notification-worthy domain event occurred. A future `notifications` app owns inbox state, delivery channels, read/unread state, preferences, retries, and external delivery.

### 16.2 Mandatory work notification events

```text
work_created
work_assignment_requested
work_assignment_accepted
work_assignment_rejected
work_clarification_requested
work_routing_requested
work_routing_escalated
work_ownership_transfer_requested
work_ownership_transfer_accepted
work_ownership_transfer_rejected
work_started
work_blocked
work_unblocked
work_deadline_approaching
work_deadline_missed
work_review_requested
work_changes_requested
work_review_approved
work_closure_submitted
work_closed
work_reopened
work_archived
work_restored
external_notification_required
```

Equivalent task events must be emitted where applicable.

### 16.3 Transactional outbox

The work module must use a transactional outbox record now, in this build:

- created in the same database transaction as the domain change;
- immutable payload version;
- idempotency key;
- event type;
- aggregate ID and version;
- actor and organization scope;
- recipient-resolution references where applicable;
- processing status;
- retry count and last error metadata;
- no external network call inside the work transaction.

A general user-notification table must not be hidden inside `work`.

Every important work mutation must atomically create:

- work state change;
- work history entry;
- domain event envelope;
- outbox event record.

The database transaction is the authority boundary. If the transaction rolls back, none of those records exist. If the transaction commits, the durable event envelope exists even if downstream delivery is delayed or unavailable. `WorkOutboxEvent` is the authoritative envelope for now; a separate universal event ledger can be projected later.

### 16.4 Background worker orchestration

The work module has enough asynchronous load to justify a background worker layer. Celery is required for retryable, non-authoritative follow-up processing, not for lifecycle decisions.

Celery is allowed to process:

- notification dispatch;
- deadline reminder generation;
- overdue detection;
- escalation processing;
- attachment and evidence inspection jobs;
- file-processing requests;
- periodic integrity validation;
- derived visibility refreshes;
- search indexing and analytics projection jobs;
- outbox consumption and retry handling.

Celery must not process:

- ownership transfer authority;
- assignment acceptance authority;
- review approval authority;
- closure authority;
- any direct state mutation that would bypass the synchronous work service and PostgreSQL transaction.

Correct execution flow:

1. API request validates permission and hierarchy.
2. API service opens a PostgreSQL transaction.
3. API service updates work state.
4. API service writes status transition, history, and outbox rows.
5. API service commits the transaction.
6. A post-commit trigger schedules background processing, typically via `transaction.on_commit()`.
7. Celery workers poll or consume committed outbox records and process side effects.

`transaction.on_commit()` is a dispatch trigger only. It is not the source of durability. The transactional outbox is the durable contract that protects against process death after commit and before task publication.

### 16.5 Foundational event ledger

MintFlow should have a small standalone `events` module if the project is moving beyond a single app prototype. This is justified by the long-term requirements for accountability, institutional memory, AI reasoning, search, analytics, and later audit interpretation.

The `events` module must own:

- generic domain-event envelope;
- append-only event storage;
- correlation and causation identifiers;
- event schema versions;
- publication services;
- idempotency tracking for event publication;
- retention and partitioning strategy;
- projection-friendly read models when needed.

The `events` module must not own:

- work lifecycle rules;
- work status transitions;
- assignment authority;
- review authority;
- closure authority;
- document truth;
- permission decisions;
- organization hierarchy;
- authentication state.

The `work` module owns what a work event means. The `events` module owns how durable event history is stored and published. `WorkStatusTransition` is the authoritative domain history for work. A `DomainEvent` is the integration/history envelope derived from that change. Both are required, but they solve different problems.

If the `events` module is implemented in this build, every important work mutation must atomically create the work-state change, the work-history record, the durable domain-event row in `events`, and the outbox/publication record in the same PostgreSQL transaction. In that mode, `WorkOutboxEvent` is transport/publication state, not the long-term event store.

### 16.6 EVENTS.md contract

The dedicated `EVENTS.md` contract for the `events` module must be written before implementation of any event-driven projection or external consumer. It is a required foundation document, not an optional note.

#### 16.6.1 Purpose

The `events` module is the project-wide historical event backbone. It stores durable, append-only event envelopes for domain changes emitted by MintFlow modules. It exists so that later audit, analytics, AI reasoning, search indexing, and cross-module projections can consume a stable event stream without depending on live transactional tables.

#### 16.6.2 Ownership

The `events` module owns:

- generic event envelope storage;
- append-only event history;
- correlation identifiers;
- causation identifiers;
- event schema versioning;
- publication state;
- retry state;
- dead-letter handling;
- retention and partitioning policy;
- projection metadata for downstream consumers.

The `events` module does not own:

- any business lifecycle rules;
- work state transitions;
- assignment authority;
- review authority;
- closure authority;
- document/file truth;
- permissions;
- identity;
- organization hierarchy;
- audit interpretation.

#### 16.6.3 Domain boundary

`work` defines what happened in work terms. `events` stores the durable event envelope for that change. A `WorkStatusTransition` remains the authoritative work-history record. A `DomainEvent` records the integration-grade event representation for the same mutation. They are intentionally not the same model.

#### 16.6.4 Required event envelope

Every persisted event row must carry, at minimum:

- event ID;
- event type;
- aggregate type;
- aggregate ID;
- organization ID when the event is organization-scoped;
- actor ID when known;
- occurred at;
- schema version;
- payload JSON;
- correlation ID, nullable;
- causation ID, nullable;
- idempotency key, unique;
- publication status;
- attempt count;
- available at;
- locked at, nullable;
- processed at, nullable;
- last error code, nullable;
- last error message, nullable;
- created at;
- updated at.

#### 16.6.5 Required states

```text
pending
processing
processed
failed
dead_lettered
```

#### 16.6.6 Event semantics

- Events are append-only.
- Events are never updated to change business meaning after publication.
- A failed publish does not erase the original event row.
- Retries must be idempotent.
- Dead-lettered events remain queryable and inspectable.
- Event payloads must be schema-versioned so future projections can evolve safely.

#### 16.6.7 Work integration contract

For work mutations that matter for accountability, the same PostgreSQL transaction must produce:

- the authoritative work-state change;
- the work history record;
- the durable event envelope in `events`;
- the outbox/publication record used by Celery.

The work module remains the source of truth for the meaning of the event. The events module remains the source of truth for the durable event stream. `WorkOutboxEvent` is the bridge between the work transaction and the event stream, not a competing long-term ledger.

#### 16.6.8 Retry and recovery

- A Celery worker may consume committed events or outbox rows idempotently.
- A scheduled sweeper may requeue stalled or abandoned records.
- Recovery tasks must never mutate authoritative work state.
- Recovery tasks may only publish, retry, project, or reconcile event delivery state.

#### 16.6.9 Downstream use

The event stream may later feed:

- notifications;
- search;
- analytics;
- projection stores;
- audit interpretation;
- AI reasoning support;
- future event-ledger consumers.

No downstream consumer may be allowed to redefine the business meaning of the event.

### 16.7 Redis / Valkey boundary

Redis or Valkey may be introduced narrowly as infrastructure support. It is useful for throughput and latency, but it must never become a source of truth.

Recommended initial uses:

- Celery broker;
- short-lived cache;
- permission-decision cache;
- hierarchy-resolution cache;
- throttling support;
- temporary worker coordination.

Redis or Valkey must not become the source of truth for:

- assignments;
- work status;
- notification records;
- review decisions;
- hierarchy history;
- audit records;
- permission grants;
- event history.

Redis Pub/Sub must not be used for authoritative work events because at-most-once delivery can lose messages. If event delivery matters, the durable path is PostgreSQL outbox plus idempotent consumer processing.

Correct flow:

1. Work mutation commits in PostgreSQL.
2. Work state, history, domain event, and outbox row are written atomically.
3. Celery consumes the committed outbox record.
4. Redis or Valkey may support broker coordination or cache retrieval, but never replace the outbox.

Cache invalidation rules:

- cache keys for hierarchy and permission decisions should include `organization_id`, `actor_id`, `organization_structure_version`, `permission_revision`, and `resource_scope` or equivalent scope markers;
- when organization hierarchy, reporting lines, position assignments, delegations, role bindings, grants, or denials change, the relevant revision must change or the cache must be invalidated;
- never rely only on time-based expiry for security-sensitive authorization caches;
- cache is a performance hint, not a trust boundary.

### 16.8 CACHE.md contract

The dedicated `CACHE.md` contract for Redis or Valkey usage must exist before any security-sensitive cache is implemented. It is a required architecture document, not an optimization note.

#### 16.8.1 Purpose

The cache layer exists to reduce repeated read cost for derived values that are safe to recompute. It must not become a second system of record.

#### 16.8.2 Allowed cached data

Only derived, reconstructable, non-authoritative data may be cached. Examples:

- permission-decision results for short-lived reuse;
- hierarchy-resolution results for a specific organization/actor/revision combination;
- lookup accelerators for visible work lists;
- throttle counters;
- temporary worker coordination data;
- idempotency hints where the authoritative key remains in PostgreSQL.

#### 16.8.3 Forbidden cached data

The cache must never be the source of truth for:

- work assignments;
- work status;
- work history;
- event history;
- notification delivery records;
- review decisions;
- permission grants or denials;
- hierarchy history;
- document truth;
- audit records.

#### 16.8.4 Invalidations

Cache invalidation must be deterministic and tied to revision changes, not only time-to-live expiry.

Required revision inputs for security-sensitive cache keys:

- `organization_id`;
- `actor_id`;
- `organization_structure_version`;
- `permission_revision`;
- `resource_scope`;
- `document_version` when document visibility is involved.

Whenever hierarchy, reporting lines, position assignments, delegations, role bindings, grants, denials, or document visibility changes, the relevant revision must change or the cache entry must be explicitly invalidated.

#### 16.8.5 Safety rules

- Redis or Valkey Pub/Sub must not be used for authoritative work events.
- Cache misses are acceptable; stale authorization is not.
- A cache entry may speed up a decision, but it must never authorize an action on its own.
- The authoritative decision remains in PostgreSQL-backed application logic.
- If the cache is unavailable, the system must degrade safely by recomputing from source of truth.

#### 16.8.6 Operational notes

- use short TTLs for derived security-sensitive entries even when revision keys exist;
- prefer explicit invalidation on write paths over blind expiration;
- do not cache confidential payloads longer than necessary;
- treat the cache as disposable infrastructure.

### 16.9 Document/file foundation

MintFlow requires a minimal document/file foundation before work evidence uploads are enabled. This must be a single canonical document/file foundation, implemented either as a standalone `documents` module or as a separate local file foundation service, but not both. It must be domain-neutral and project-wide.

The document/file foundation must own:

- document/file truth;
- storage zone;
- storage path;
- original filename;
- safe filename;
- MIME type;
- detected MIME type;
- size in bytes;
- SHA-256 checksum;
- uploaded by;
- uploaded at;
- classification level;
- retention policy;
- malware scan status;
- verification status;
- source type.

The document/file foundation must not own:

- work semantics;
- evidence meaning;
- review authority;
- assignment authority;
- permissions;
- organization hierarchy;
- audit interpretation.

Work must only store opaque `document_id` references and work-side provenance records. It must not store raw file paths, binary blobs, or uncontrolled `FileField` truth. The document foundation remains the source of truth for the file, its scan status, and its retention/classification metadata.

Work evidence upload endpoints must remain disabled until this foundation exists and is documented. The implementation may use the existing `WorkAttachment` ledger for provenance, but the logical evidence relation must also be represented explicitly as `WorkEvidenceLink` in the work domain contract.

- actor;
- payload JSON with documented schema;
- idempotency key, unique;
- created at;
- processing status;
- attempts;
- available at;
- locked at, nullable;
- processed at;
- last error code/message with sensitive-data restrictions.

Recommended states:

- `pending`
- `processing`
- `processed`
- `failed`
- `dead_lettered`

Operating rule:

- a Celery worker consumes committed outbox rows idempotently;
- a scheduled sweeper retries pending or abandoned rows that were not processed due to worker crash, broker outage, or stale lock expiration;
- the worker never mutates authoritative work state;
- the worker only performs retryable side effects and projections.

### 19.16 `WorkAttachment`

Purpose: history-preserving provenance record for any document or file reference associated with work, tasks, activities, evidence, reviews, or closure.

Key fields:

- work;
- optional task;
- optional activity;
- optional evidence;
- optional review round;
- optional closure;
- document reference;
- document version reference;
- attachment role;
- attached by;
- attached at;
- detached by, nullable;
- detached at, nullable;
- attachment reason;
- visibility classification;
- sensitivity classification;
- source document service;
- checksum snapshot;
- MIME type snapshot;
- size snapshot;
- is primary;
- created at;
- updated at.

Rules:

- one row records one attachment occurrence;
- document reference and document-version reference are opaque identifiers from the document service, not file paths;
- detaching a document never deletes the row;
- reattaching the same document later creates a new row rather than reusing old history;
- work must never store raw file paths or binary blobs;
- document security and raw-file access remain owned by the document service.

### 19.17 `WorkEvidenceLink`

Purpose: explicit work-side relationship between a work item and a document-backed evidence item.

Key fields:

- work item;
- optional task;
- optional activity entry;
- document_id;
- evidence_type;
- submitted_by;
- verification_status;
- linked_at;
- visibility classification;
- created at;
- updated at.

Rules:

- document_id is an opaque identifier from the document foundation;
- the work domain owns the relationship and evidence semantics, not the file truth;
- the document foundation owns upload, storage, scan, retention, and file metadata;
- the implementation may unify this with `WorkAttachment` only if no semantics are lost and the evidence-specific contract remains explicit.

## 23. Policy engine requirements

For every endpoint and permission-sensitive service action:

- register the `work` application and related policy models;
- use stable lowercase permission keys;
- categorize create/read/list/update/delete/custom actions;
- assign risk level;
- map to UI-friendly permission categories;
- declare dependencies;
- create/update endpoint version records;
- append policy changelog entries;
- run registry synchronization and strict validation.

Examples of required dependency thinking:

- `work.work_item.close` requires `work.work_item.read` and appropriate review/closure authority.
- `work.work_item.archive` requires `work.work_item.read` and may imply loss of ordinary-list visibility.
- `work.attachment.create` requires `work.work_item.read` plus a document upload/attach permission when the document service exists.
- `work.attachment.detach` requires `work.attachment.list` or `work.work_item.read` plus a manage-attachment permission.
- `work.evidence.verify` requires `work.evidence.read`.
- `work.review.decide` requires `work.review.list` or read-detail capability.
- `work.work_item.transfer_ownership` requires read access and assignment authority.

Claude must update policy metadata in the same implementation task. Endpoint code without policy lifecycle metadata is incomplete.

## 24. Integration contracts

### 24.1 `authenticate` integration

Work needs:

- stable actor/user FK;
- actor active/login eligibility status where relevant;
- system/service-account identity for automated events;
- no password/security logic.

Rules:

- an inactive actor cannot accept new ownership or assignment;
- disabling login does not automatically erase actor history;
- service accounts may create system activities only when explicitly permitted and attributable.

### 24.2 `organization` integration

Work needs:

- organization and unit references;
- closure-table ancestor/descendant queries;
- active memberships;
- active unit memberships;
- active position assignments;
- reporting-line resolution;
- unit-head resolution;
- root hierarchy resolution;
- delegation resolution;
- historical/effective-date context.

The organization module remains authoritative. Work may cache immutable snapshots for audit, but not maintain a second organization tree.

### 24.3 `permissions` integration

Every controlled action must call the existing permission-decision interface with:

- subject actor;
- permission key;
- organization scope;
- organization-unit scope where relevant;
- explain/decision context when supported.

Work then applies resource and lifecycle checks. Work must not write roles, grants, or denials.

### 24.4 `core.policy_engine` integration

All routes/actions are registered, categorized, versioned, and validated. No endpoint is complete without policy metadata.

### 24.5 `core` integration

Use:

- standard JSON success/error envelope;
- central exception handling;
- request ID;
- structured logging;
- standard pagination;
- configured JWT/service-account authentication;
- default throttling and explicit expensive-endpoint throttles.

### 24.6 Future `notifications` integration

Input: outbox events with recipient-resolution references.  
Output: inbox/delivery status.  
Work does not own channel preferences or delivery retries.

### 24.7 Future `events` integration

Work status, activity, assignment, review, and closure events should be projectable into a universal event ledger. The work outbox is the transition bridge until that module exists.

### 24.8 Future `documents` integration

Documents own physical file truth and metadata. Work owns evidence purpose, attachment provenance, and linkage.

Minimum document-service requirements for government-grade use:

- document versioning must be immutable and attributable;
- raw files must never be exposed through work database tables;
- upload, download, preview, revoke, and archive actions must all be permissioned and audited;
- work must only store references and security-relevant snapshots, not storage paths or blobs;
- access to a document from work does not imply access to every version or every attachment context;
- document-level ACLs must be narrower or equal to work-level visibility, never broader by accident.

### 24.9 Future `cases` integration

A case may contain multiple work items. Do not add a phantom unvalidated case UUID field before the cases app contract exists. When implemented, add a documented nullable FK or association with migration and compatibility plan.

### 24.10 Future `workflow` integration

The work module owns its core lifecycle invariants. A future workflow module may define configurable stages and transitions but must invoke work services and use the same dynamic hierarchy resolver. It must not bypass work state rules.

### 24.11 Future `audit` integration

Audit consumes immutable work transitions, activities, reviews, evidence verification, and hierarchy snapshots. Audit findings are not stored as ordinary work comments.

### 24.12 Future `evaluation` integration

Evaluation consumes factual metrics and contextual organization data. It owns normalized performance interpretation.

### 24.13 Future AI integration

AI may:

- suggest task decomposition;
- draft summaries;
- suggest likely routing;
- identify possible blockers;
- summarize activity/evidence;
- recommend reviewers.

AI may not autonomously:

- transfer ownership;
- approve review;
- close work;
- archive work;
- alter evidence verification;
- create performance judgments;
- bypass permissions or hierarchy.

AI suggestions must be stored as drafts/recommendations with model, prompt version, source references, confidence/uncertainty, and human decision.

## 27. Concurrency, idempotency, and consistency

### 27.1 Optimistic concurrency

Use an `aggregate_version` on work and task current-state rows.

Mutation requests should accept an expected version through request data or an `If-Match`/ETag strategy documented in API contracts. A stale mutation returns `409 WORK_VERSION_CONFLICT`.

### 27.2 Row locking

Use row-level locking for:

- assignment acceptance;
- ownership transfer response;
- routing response;
- status transitions;
- review decisions;
- closure;
- reopen/archive/restore;
- task reorder where concurrent ordering matters.

### 27.3 Idempotency

Idempotency keys are mandatory for:

- create work;
- assignment/transfer acceptance;
- review decision;
- closure;
- external notification request;
- outbox processing.

Repeated requests with the same key and same payload return the prior result. Same key with different payload returns a conflict.

### 27.4 Transaction boundary

Current state, append-only history, hierarchy snapshot, domain event, and outbox event must commit atomically.

No email, SMS, external API call, OCR call, or AI call is permitted inside the work transaction.

## 29. Security and privacy requirements

- Deny by default.
- Validate organization and unit scope on every action.
- Never trust actor/unit IDs supplied by the client without authoritative lookup.
- Never expose work existence through list/detail differences for unauthorized users.
- Filter nested activity/evidence at the query layer.
- Do not log confidential work text, evidence content, contact details, tokens, or raw files.
- Log request ID, actor ID, action key, work ID, result code, and safe metadata.
- Use explicit serializer read/write fields.
- Prevent mass assignment of creator, owner, responsible unit, status, closure outcome, review decision, and audit fields.
- MIME, malware, checksum, and storage validation belong to document integration.
- External stakeholder contacts require field-level access control and future retention rules.
- No background task may mutate work without an attributable system/service actor and permission context.

## 36. Acceptance criteria

The work module is acceptable only when all of the following are demonstrable:

1. Every active work has one current accountable actor and responsible unit.
2. Creator and historical ownership are preserved.
3. Work cannot be hard deleted.
4. Status and ownership cannot be arbitrarily patched.
5. Tasks/subtasks support safe hierarchical execution without cycles.
6. Dynamic hierarchy resolves responses, reviews, visibility, and escalation.
7. Every hierarchy-driven decision stores an immutable snapshot.
8. Organization changes affect future actions but never rewrite prior history.
9. Ownership does not silently change after hierarchy restructuring.
10. Cross-unit routing preserves accountability and detects loops.
11. Activity entries provide correction-based audit history.
12. Review-required work cannot close without review approval.
13. Review rounds preserve stable submission snapshots.
14. Closure stores an explicit outcome and supporting explanation.
15. External stakeholders receive only approved communications.
16. Permission evaluation and resource visibility both pass before access.
17. Sensitive nested data is filtered at query level.
18. Current-state changes, history, hierarchy snapshots, and outbox events are atomic.
19. Concurrent conflicting actions are detected.
20. Policy engine registry and strict validation pass.
21. Integrity command detects deliberately corrupted scenarios.
22. API, data contract, integration, lifecycle, events, and debug documentation exist.
23. Required test suites pass against PostgreSQL.
24. `ruff check`, `ruff format`, migrations, policy validation, and project CI gate pass.

## 37. Final architectural statement

MintFlow's work module must be implemented as:

> An auditable work-execution aggregate whose lifecycle is stable, whose authority and response paths are dynamically derived from the effective organizational hierarchy, whose historical decisions remain immutable, and whose integrations preserve the ownership boundaries of identity, organization, permissions, policy governance, evidence, notification, audit, and evaluation.

The hierarchy is not decorative metadata. It is an active runtime authority graph.

The workflow must therefore be dynamic in **who responds, reviews, sees, receives, and escalates**, while remaining strict and deterministic in **what lifecycle transitions are allowed**.
