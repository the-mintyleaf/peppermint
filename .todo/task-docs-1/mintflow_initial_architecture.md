# MintFlow — Initial Architecture Thought Process

**Document status:** Initial grounding document  
**Purpose:** Keep the project direction stable while building a complex AI-powered organizational intelligence platform.  
**Scope:** Backend/system architecture, module segmentation, local-first infrastructure, polyglot database strategy, and AI-assisted engineering boundaries.  
**Important note:** This is not the final implementation specification for every module. It is the initial thought process and architectural anchor so that the project does not drift into chaos as individual apps are designed and built.

---

## 1. Why this document exists

MintFlow is not intended to be just a normal Kanban system.

The long-term objective is to build an **AI-powered organizational operating system** for work assignment, work monitoring, work auditing, work evaluation, case tracking, institutional memory, and advanced reasoning.

The system must support organizations ranging from small teams to large privacy-sensitive institutions such as government ministries. Because of this, the architecture must be:

- local-first;
- privacy-first;
- audit-first;
- scalable;
- modular;
- polyglot-database ready;
- AI-assisted but not AI-chaotic;
- strict about source-of-truth ownership;
- designed for long-term organizational history.

This document exists so that every future AI-assisted coding session remains grounded in the same system vision.

---

## 2. Core product idea

MintFlow will help an organization understand and improve how it functions.

At the highest level, the system should be able to answer:

- Who exists in the organization?
- Where does each person belong?
- What authority does each person have?
- What work was assigned?
- Who assigned it?
- Who performed it?
- What case, file, project, or event did the work contribute to?
- What documents, OCR outputs, logs, evidence, and decisions were produced?
- Where did delays happen?
- Which departments are overloaded?
- Which roles are inefficiently structured?
- Which workflows are healthy or unhealthy?
- What should leadership review or improve?

The system should not only track current state. It should preserve **historical reality**.

Normal Kanban systems usually track:

```text
Todo → Doing → Done
```

MintFlow should track:

```text
Organization → Authority → Case → Work → Workflow → Event → Evidence → Audit → Evaluation → AI Reasoning
```

## 3. Foundational domain concepts

### 3.1 In-App Users

All users who access the system.

Engineering meaning:

```text
User / Actor / Principal
```

Users may be:

- employees;
- supervisors;
- administrators;
- auditors;
- AI/system actors;
- external reviewers in later phases.

The user identity system should only answer:

```text
Who is this actor?
Can this actor authenticate?
Is this actor active?
```

It should not own organization hierarchy, roles, permissions, or work authority.

---

### 3.2 Work

Work is any task, duty, assignment, review, approval, recurring responsibility, generated action, or operational activity performed by a user or system.

Work may be:

- manually created;
- assigned by a supervisor;
- generated by workflow rules;
- generated by AI recommendation after human approval;
- recurring;
- case-linked;
- department-linked;
- file-linked;
- evidence-producing.

Work should not be treated as a simple task only. Work is an auditable organizational action.

---

### 3.3 Case

A case is a long-term historical container.

A case may represent:

- a government file;
- a project;
- an event;
- an incident;
- a complaint;
- a procurement process;
- a legal matter;
- an investigation;
- a recurring institutional process;
- a research trail;
- an operational issue.

A case collects:

- work;
- documents;
- OCR outputs;
- comments;
- decisions;
- events;
- audit trails;
- external intelligence;
- AI summaries;
- timelines;
- classification metadata;
- performance/evaluation context.

A case is the system's main container for organizational memory.

## 4. Core philosophy

The system must be designed around this principle:

```text
Every important action must be traceable to who, where, what, when, why, and under what authority.
```

In engineering terms:

```text
actor       → user, system, or AI actor
scope       → organization, unit, role, case, work item, file, workflow stage
action      → policy permission key or event type
time        → when the action happened
reason      → user reason, system reason, AI reason, policy reason
authority   → role, position, delegation, permission grant, policy decision
source      → document, OCR output, case event, web source, manual input
```

If this traceability is maintained from the beginning, later audit, evaluation, and AI reasoning will be much stronger.

---

## 5. Local-first and privacy-first requirement

MintFlow must be designed as a system that can run fully inside a private organizational network.

Default assumptions:

- no hosted cloud storage;
- no S3 dependency;
- no external managed database dependency;
- no external hosted AI dependency;
- local LLM by default;
- local OCR pipeline by default;
- local search/indexing infrastructure;
- local backups and disaster recovery;
- air-gap capable deployment where required.

The system may later support optional integrations, but no critical path should require external hosting.

This is especially important for ministries, government agencies, legal institutions, investigation units, and privacy-sensitive enterprises.

The current backend foundation is:

```text

PostgreSQL
JWT authentication
Policy Engine inside core/policy_engine/
React frontend separately
```

The current engineering rules prioritize:

- no logic in views;
- no schema change without migration and data contract update;
- no undocumented app boundary;
- no undocumented database engine;
- no endpoint change without policy engine lifecycle update;
- no completion claim without tests;
- no careless dependency additions.

This discipline must continue throughout the project.

## 7. Policy Engine role

The Core Policy Engine is already the first foundation.

It should own:

- application metadata;
- model/entity metadata;
- endpoint metadata;
- permission keys;
- permission categories;
- dependency relationships;
- endpoint versions;
- policy changelogs;
- backward and forward compatibility notes.

It should not own:

- users;
- passwords;
- departments;
- roles;
- memberships;
- permission assignments;
- organization hierarchy;
- work ownership.

The policy engine defines the **action universe** of the backend.

Example:

```text
work.work_item.create
work.work_item.assign
cases.case.read
organization.org_unit.update
permissions.role_binding.create
```

Every permission-sensitive endpoint or backend action must be registered through the policy engine lifecycle.

## 8. Highest-level system workflow

The intended system flow is:

```text
1. A user authenticates.
2. The system resolves the user's organization memberships and active positions.
3. The permission system derives authority from identity, organization, role bindings, grants, policies, and context.
4. A case is created or selected.
5. Work is created, assigned, routed, monitored, and completed.
6. Work moves through workflow stages.
7. Every important action emits an event.
8. Documents and files are attached to cases or work.
9. OCR extracts text and structure from documents.
10. Taxonomy classifies documents, cases, work, entities, topics, and risks.
11. Audit interprets events for accountability.
12. Evaluation measures workload, efficiency, delay, and organizational health.
13. Local AI reasons over structured history and source-linked evidence.
14. Human decision-makers review recommendations before organizational changes are applied.
```

The system should be event-centered, not only task-centered.

The recommended build order is:

```text
1. Policy Engine
2. Authentication / Identity
3. Organization
4. Foundational Event Ledger
5. Permissions / Authority
6. Case
7. Work
8. Workflow
9. Local File Lake / Document Metadata
10. OCR
11. Taxonomy
12. Search
13. Audit
14. Evaluation
15. Local AI Reasoning
16. Vector Search
17. Analytics Lakehouse
18. Graph Reasoning
19. Open Crawl / Intelligence
20. Reporting / Dashboards
```

This order is intentional.

Reasons:

- Permissions need organization scope.
- Audit needs events.
- OCR needs disciplined document/file storage.
- AI reasoning needs structured truth.
- Evaluation needs fair scope normalization.
- Search, vectors, graph, and analytics should be derived projections, not early sources of truth.

## 12. Polyglot database strategy

The system may eventually need multiple databases and storage engines, but each must have a clear role.

The central rule:

```text
PostgreSQL and the local file lake hold source-of-truth data.
Specialized databases are derived, rebuildable projections unless explicitly approved otherwise.
```

No database should be added because it is fashionable. It must solve a proven workload.

## 13. Recommended local-first data stack

### 13.1 PostgreSQL

Role:

```text
Primary source of truth
```

Owns:

- users;
- organizations;
- memberships;
- positions;
- policy metadata;
- roles and grants;
- cases;
- work;
- workflows;
- event ledger;
- document metadata;
- OCR job metadata;
- taxonomy metadata;
- audit records;
- evaluation configuration;
- AI recommendation records.

Scaling considerations:

- proper indexes;
- composite indexes for high-volume selectors;
- table partitioning for event logs and audit logs;
- read replicas for heavy reporting;
- strict migration discipline;
- backup/restore testing;
- point-in-time recovery;
- high availability for serious deployments.

---

### 13.2 PostGIS

Role:

```text
Spatial extension when location matters
```

Use for:

- office locations;
- ministry branches;
- jurisdiction mapping;
- incident locations;
- field inspections;
- province/district analytics;
- geo-linked cases.

Do not add separate GIS infrastructure unless PostGIS is insufficient.

---

### 13.3 Local File Lake

Role:

```text
Source of truth for large raw and derived files
```

No S3 dependency. No hosted object storage dependency.

Possible storage implementation:

```text
Early deployment:
- local filesystem
- RAID/ZFS-backed storage
- strict path conventions
- checksums
- backups

Large/private organization:
- CephFS
- enterprise NAS
- clustered local storage
- separate backup site/node
```

Recommended structure:

```text
/data/mintflow/lake/
  raw/
  processed/
  curated/
  analytics/
  archive/
  quarantine/
```

Every file must have PostgreSQL metadata:

```text
document_id
organization_id
case_id
work_item_id
storage_zone
storage_path
sha256_checksum
mime_type
size_bytes
created_by
created_at
classification_level
access_scope
retention_policy
processing_status
source_lineage
```

No app should write files randomly. File writes must go through controlled services.

---

### 13.4 Redis or Valkey

Role:

```text
Cache, locks, queue support, rate limiting
```

Use for:

- short-lived permission decision cache;
- Celery broker in early stages;
- rate limiting;
- distributed locks;
- temporary job state.

Never use as permanent audit or case history storage.

---

### 13.5 OpenSearch

Role:

```text
Derived full-text search index
```

Use later for:

- searching cases;
- OCR text search;
- document search;
- audit/event search;
- advanced filtering;
- investigation-style search.

OpenSearch must be rebuildable from PostgreSQL and the local file lake.

---

### 13.6 Qdrant

Role:

```text
Derived vector index for semantic search and RAG
```

Use later for:

- similar case retrieval;
- semantic document search;
- AI memory over case history;
- finding related files;
- retrieval-augmented generation.

Qdrant should store embeddings, not business truth.

---

### 13.7 ClickHouse

Role:

```text
Analytical projection for high-volume metrics
```

Use later for:

- performance evaluation;
- workload analytics;
- delay analysis;
- department efficiency trends;
- workflow bottleneck detection;
- audit dashboards;
- AI usage analytics.

ClickHouse should receive normalized analytical events from the event ledger.

---

### 13.8 Neo4j or graph projection

Role:

```text
Derived relationship intelligence
```

Use later when graph traversal becomes necessary.

Use for:

- person-case-document relationships;
- reporting chains;
- delegation chains;
- conflict-of-interest discovery;
- entity network reasoning;
- hidden relationship analysis;
- knowledge graph exploration.

Do not add graph infrastructure before relational relationships prove insufficient.

---

### 13.9 Kafka / Redpanda

Role:

```text
Event transport at large scale
```

Do not start with Kafka.

Start with:

```text
PostgreSQL event table + outbox pattern + Celery workers
```

Add event streaming only when there are many independent consumers:

- audit consumer;
- notification consumer;
- AI indexing consumer;
- search indexing consumer;
- analytics consumer;
- OCR consumer;
- reporting consumer.

---

### 13.10 Temporal or durable workflow engine

Role:

```text
Durable long-running workflow execution
```

Use later only if workflows become too complex for Django workflow models and Celery.

Possible use cases:

- month-long approval chains;
- retry-safe OCR/AI pipelines;
- multi-office processes;
- pause/resume workflows;
- failure recovery for long-running operations.

Start with PostgreSQL workflow models first.

## 14. Database role classification

Every store must be classified before adoption.

| Store                       | Role                        | Source of Truth?            |
| --------------------------- | --------------------------- | --------------------------- |
| PostgreSQL                  | Business truth              | Yes                         |
| Local file lake             | Raw/heavy file truth        | Yes                         |
| Redis/Valkey                | Cache, locks, queue support | No                          |
| OpenSearch                  | Search index                | No                          |
| Qdrant                      | Vector index                | No                          |
| ClickHouse                  | Analytics projection        | No                          |
| Neo4j                       | Relationship projection     | No                          |
| Kafka/Redpanda              | Event transport             | No                          |
| Temporal                    | Workflow execution state    | Conditional                 |
| Parquet/Iceberg lake tables | Analytical datasets         | Usually no, unless promoted |

The system must be able to rebuild derived stores from source-of-truth stores.

## 15. Local file lake zones

### 15.1 Raw

Original unmodified data.

Examples:

- uploaded PDFs;
- scanned images;
- original documents;
- crawl snapshots;
- imported archives.

Rule:

```text
Never mutate raw files.
```

---

### 15.2 Processed

Machine-generated intermediate outputs.

Examples:

- page images;
- OCR JSON;
- layout detection;
- table extraction;
- AI extraction drafts.

Rule:

```text
Can be regenerated from raw data.
```

---

### 15.3 Curated

Human-reviewed or approved outputs.

Examples:

- verified OCR text;
- approved classifications;
- confirmed entity records;
- validated case timelines.

Rule:

```text
Higher trust than processed data.
```

---

### 15.4 Analytics

Columnar and aggregated datasets.

Examples:

- Parquet tables;
- workload summaries;
- department performance facts;
- audit datasets;
- evaluation metrics.

Rule:

```text
Derived and rebuildable unless explicitly promoted.
```

---

### 15.5 Archive

Cold retained data.

Examples:

- closed cases;
- old documents;
- historical OCR artifacts;
- long-term ministry records.

Rule:

```text
Read rarely, retain carefully.
```

---

### 15.6 Quarantine

Untrusted or suspicious files.

Examples:

- unknown MIME files;
- corrupted documents;
- possible malware;
- unverified crawl artifacts.

Rule:

```text
No OCR or AI processing until cleared.
```

## 16. OCR and data lake relationship

OCR is a strong reason to introduce the local file lake concept.

OCR may produce:

- original source document;
- cleaned image;
- page images;
- raw text;
- layout blocks;
- table extraction;
- entity extraction;
- confidence maps;
- language detection;
- human corrections;
- AI summaries;
- embeddings;
- classification outputs.

PostgreSQL should store OCR metadata and state.

The local file lake should store heavy OCR artifacts.

Recommended OCR artifact layout:

```text
lake/
  raw/
    documents/<org_id>/<case_id>/<document_id>/original.pdf

  processed/
    ocr/<org_id>/<case_id>/<document_id>/pages/page_001.png
    ocr/<org_id>/<case_id>/<document_id>/raw_ocr.json
    ocr/<org_id>/<case_id>/<document_id>/layout.json
    ocr/<org_id>/<case_id>/<document_id>/tables/

  curated/
    documents/<org_id>/<case_id>/<document_id>/verified_text.txt
    documents/<org_id>/<case_id>/<document_id>/entities.parquet
    documents/<org_id>/<case_id>/<document_id>/classification.json
```

## 18. Permission and authority model

The permission model should connect:

```text
identity + organization + policy engine + context
```

Policy engine answers:

```text
What action exists?
```

Organization answers:

```text
Where does the user belong?
What position do they hold?
What authority chain applies?
```

Permissions app answers:

```text
Can this user perform this action under this scope and context?
```

The final access decision should look like:

```text
Can subject perform action on resource under context?
```

Where:

```text
subject = user + memberships + positions + delegations
action = policy_engine.permission_key
resource = case / work item / document / workflow / org unit
context = time, scope, sensitivity, workflow stage, emergency mode, ownership
```

Roles must be scoped. Avoid global-only role design.

Bad:

```text
User has role Manager.
```

Better:

```text
User has role Department Manager within OrgUnit X from date Y to date Z.
```

## 19. Evaluation fairness principle

Performance evaluation must not compare employees or departments unfairly.

The system must not evaluate raw task counts across unrelated roles or departments.

Unfair comparison:

```text
Compare IT support staff, legal reviewers, finance officers, and field investigators using one raw productivity score.
```

Fair comparison:

```text
Compare users only within similar role scope, workload category, authority level, department context, case complexity, and time period.
```

Evaluation must consider:

- role scope;
- department type;
- case complexity;
- assigned workload;
- authority level;
- resource availability;
- recurring vs generative work;
- workflow stage;
- organizational constraints;
- delay reasons;
- dependency blockers.

AI may recommend organizational change, but human leadership must review and decide.

Correct:

```text
AI recommends that Unit A may need more reviewers because evidence shows backlog growth, delay concentration, and high work complexity.
A human reviews the recommendation, evidence, and context.
The system records the final decision.
```

Wrong:

```text
AI automatically declares an employee or department inefficient based only on raw task count.
```

## 20. AI role in the system

AI should be used for:

- summarization;
- case reasoning;
- document understanding;
- OCR assistance;
- classification suggestions;
- timeline generation;
- workload explanation;
- similar case retrieval;
- anomaly detection;
- organizational recommendation;
- research support;
- natural language querying.

AI must not be the default source of truth.

AI output should usually be stored as:

```text
recommendation
suggestion
draft
classification_candidate
summary_candidate
extraction_candidate
```

Human-reviewed or system-approved AI output may later be promoted to curated knowledge.

Every AI output should ideally record:

- model used;
- prompt/template version;
- input source references;
- output version;
- confidence or uncertainty where applicable;
- reviewer status;
- linked case/work/document;
- created_at;
- created_by system actor.

## 21. Open crawl and external intelligence

Open crawl / intelligence should come later, after internal data foundations are stable.

External intelligence may support:

- public event tracking;
- organization-related news;
- case context;
- public documents;
- web research;
- timeline enrichment;
- source comparison.

Rules:

- external data must have source lineage;
- crawl artifacts must be stored in local file lake;
- extracted facts must not be blindly trusted;
- source credibility should be tracked;
- web intelligence should link to cases/events only through reviewable records;
- crawl systems must respect legal, ethical, and operational boundaries.

Open crawl should enrich cases. It should not pollute internal truth.

## 24. What not to do

Do not:

- build every database immediately;
- use cloud object storage as a default assumption;
- let AI create apps without contracts;
- place business logic in `core/`;
- mix organization logic into permissions;
- mix permission assignment into authentication;
- build OCR before disciplined document/file storage;
- build audit without an event ledger;
- build evaluation from raw task counts only;
- allow AI recommendations to become automatic decisions;
- create direct app-to-app coupling without documented contracts;
- let derived databases become undocumented truth stores;
- store files without checksum, metadata, owner, access policy, and retention rule.

## 25. AI-assisted development rules for this project

Every AI coding agent working on MintFlow must assume:

```text
1. This system may be deployed in a private ministry network.
2. No external storage service is allowed by default.
3. No hosted AI service is required by default.
4. Local LLM and local OCR are preferred.
5. Data volume may become very large.
6. PostgreSQL is the main business source of truth.
7. Local file lake is the source of truth for heavy raw files.
8. Search, vector, graph, and analytics databases are derived unless explicitly approved otherwise.
9. Every new database must declare its role: truth, cache, projection, index, archive, or transport.
10. Every schema must consider indexing, partitioning, retention, backup, and auditability.
11. AI output must include source references and review state.
12. Privacy, auditability, recovery, and correctness matter more than speed.
13. No module should be built without a data contract.
14. No endpoint should be built without policy engine metadata.
15. No major architecture addition should happen without written approval.
```

## 28. Final grounding statement

MintFlow should be engineered as:

```text
A local-first, privacy-first, AI-powered organizational intelligence platform
that tracks work, cases, authority, events, evidence, audit, and evaluation
with strict data contracts, governed polyglot databases, and human-reviewable AI reasoning.
```

This is the initial thought process.

It should guide the project without becoming a prison. The system must remain open-minded, but every expansion must be engineered with discipline.

The goal is not to quickly assemble features.

The goal is to build a system that can become trustworthy enough for real organizations, including ministries, to use for work tracking, accountability, institutional memory, and intelligent decision support.
