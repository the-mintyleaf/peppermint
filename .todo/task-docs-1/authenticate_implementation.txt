# MintFlow Authenticate App — Concept and Implementation Requirement

**Document status:** Concept / Claude Code implementation handoff  
**Target app:** `authenticate`  
**System:** MintFlow backend  
**Stack:** Django + Django REST Framework + PostgreSQL + JWT via SimpleJWT  
**Security target:** Ministry-grade, local-first, privacy-first authentication foundation  
**Date:** 2026-06-22

---

## 1. Purpose

This document defines the first serious authentication module for MintFlow.

The `authenticate` app is the entry point through which actors enter the software. It must be secure, auditable, efficient, and robust enough for sensitive deployments such as government ministries, legal institutions, investigation units, and large private organizations.

This app must be **small in responsibility but strong in security**.

It answers only:

```text
Who is this actor?
Is this actor registered?
Is this actor allowed to use the software login system?
Can this actor authenticate safely?
What authentication/security events happened?
```

It must not answer:

```text
Which organization unit does this actor belong to?
Which department does this actor work in?
What official position does this actor hold?
What role grants does this actor have?
What cases, work items, documents, or workflows can this actor access?
```

Those concerns belong to later modules:

```text
organization  → structure, membership, position, history
permissions   → RBAC / ABAC / HBAC / scoped authority decisions
events        → formal system event ledger
audit         → accountability interpretation
```

---

## 2. Architectural boundary

The app name is:

```text
authenticate
```

Do not rename it to `accounts`, `users`, `identity`, or `auth` unless the human owner explicitly approves.

The `authenticate` app owns:

```text
registered actors
login eligibility
credential state
JWT/session state
authentication security events
password lifecycle
MFA readiness / MFA implementation when approved
authentication endpoint policy metadata
```

The `authenticate` app must not own:

```text
organization hierarchy
departments
positions
roles
permission assignment
case authority
work assignment authority
policy-engine internals
```

The policy engine defines what actions exist. Authentication defines who the actor is and whether the actor can enter the system.

---

## 3. Core design principle

Treat a user as an **actor / principal**, not merely as someone who can log in.

An organization may have many registered people or system actors who exist in records but do not use the software directly. Therefore, the system needs a clear distinction between:

```text
actor exists in MintFlow
actor is active as a record
actor is allowed to log in
actor is staff/admin
actor is superuser/emergency root
```

This is critical for government and institutional systems because some actors may appear in case history, work history, organization records, audit trails, or external review workflows without having software login access.

---

## 4. Actor login flags

The `User` model must distinguish these fields clearly:

| Field | Meaning |
|---|---|
| `is_active` | Actor record is valid and not removed from operational use. |
| `is_login_enabled` | Actor is allowed to authenticate into the software. |
| `account_status` | Lifecycle state of the account/actor. |
| `is_staff` | Temporary platform/staff access flag before the permissions app exists. |
| `is_superuser` | Emergency/root platform authority only. Must be protected heavily. |

Example:

```text
An employee exists in the system but does not use the software:

is_active = true
is_login_enabled = false
account_status = active
```

This actor can later appear in organization records, work records, events, cases, or audit history, but login must be blocked.

---

## 5. Recommended account lifecycle states

Use a `TextChoices` enum in `authenticate/constants.py`.

```text
pending
active
suspended
deactivated
archived
```

Meaning:

| State | Login allowed? | Meaning |
|---|---:|---|
| `pending` | No | Actor created but not activated. |
| `active` | Depends on `is_login_enabled` | Actor is valid and operational. |
| `suspended` | No | Temporarily blocked. |
| `deactivated` | No | No longer operational. |
| `archived` | No | Historical actor only. |

Login must require all of these:

```text
is_active = true
is_login_enabled = true
account_status = active
not locked
valid credentials
MFA passed if MFA is required
```

## 6. Security posture

This module should target an **OWASP ASVS Level 2 style** authentication posture.

This does not mean claiming formal certification. It means the design must be strong enough for serious institutional deployments and must include controls for common authentication failures:

```text
weak password handling
credential stuffing
brute-force login attempts
account enumeration
token theft
token replay
improper logout
session fixation style mistakes
insecure cookie flags
missing audit logs
sensitive data leakage in logs
staff/admin account abuse
```

The module must use stable, maintained Django ecosystem libraries where appropriate. Do not invent custom cryptography, token signing, password hashing, OTP generation, or credential storage.

## 8. Password hashing documentation requirement

The password hashing algorithm must be explicitly documented before implementation is considered complete.

Create or update:

```text
authenticate/docs/SECURITY.md
authenticate/docs/DATA_CONTRACT.md
authenticate/docs/API.md
backend/core/docs/THIRD_PARTY_LIBRARIES.md  # only if new dependency is added
```

The documentation must state:

```text
1. Which Django password hasher is used by default.
2. Exact import path of the hasher.
3. Algorithm name.
4. Whether the algorithm is memory-hard or CPU-hard.
5. Required third-party dependency, if any.
6. PASSWORD_HASHERS order in settings.
7. Whether older hashers are retained for legacy password verification.
8. Password upgrade behavior after successful login.
9. Why this hasher was chosen.
10. How the configuration is verified in tests.
11. Migration/rollback considerations.
12. Operational notes for production hardware sizing.
```

Preferred high-security configuration:

```python
PASSWORD_HASHERS = [
    "django.contrib.auth.hashers.Argon2PasswordHasher",
    "django.contrib.auth.hashers.PBKDF2PasswordHasher",
    "django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher",
    "django.contrib.auth.hashers.BCryptSHA256PasswordHasher",
]
```

Notes:

```text
- Argon2PasswordHasher is preferred for serious deployments if argon2-cffi is approved and installed.
- PBKDF2PasswordHasher is acceptable as the baseline Django-compatible fallback.
- Never write a custom password hashing function.
- Never store raw passwords.
- Never log passwords.
- Never expose password hash values through API serializers.
```

If Argon2 is not approved yet, Claude must implement using Django's approved default hasher and document that Argon2 is a recommended future hardening step.

## 9. Recommended models

Create these models in `authenticate/models.py`.

All models must define `__str__`.
All public-facing IDs must be UUIDs.
All timestamps must be timezone-aware.
All enums must live in `authenticate/constants.py`.
All data contracts must be documented before model code is written.

### 9.1 `User`

Purpose:

```text
Represents a registered actor/principal in MintFlow.
```

Recommended fields:

```text
id                          UUID primary public identifier
username                    unique login identifier
email                       unique nullable/blank depending deployment policy
display_name                required human-readable name
actor_type                  human | system | ai | external
account_status              pending | active | suspended | deactivated | archived
is_login_enabled            boolean
is_active                   boolean
is_staff                    boolean
is_superuser                boolean
password                    Django-managed hash
last_login                  nullable datetime
created_at                  datetime
updated_at                  datetime
```

Rules:

```text
- Use a custom Django user model from the start.
- Do not expose password hash in serializers.
- Do not place organization membership fields here.
- Do not place role/permission fields here.
- System and AI actors should use unusable passwords unless a service-account authentication design is later approved.
```

### 9.2 `UserSecurityState`

Purpose:

```text
Tracks security posture and credential lifecycle state for a user.
```

Recommended fields:

```text
id
user                        OneToOneField(User)
password_changed_at         nullable datetime
password_change_required    boolean
failed_login_count          integer
locked_until                nullable datetime
lock_reason                 blank text/choice
mfa_required                boolean
mfa_enrolled                boolean
last_failed_login_at        nullable datetime
last_successful_login_at    nullable datetime
last_password_reset_at      nullable datetime
created_at
updated_at
```

Rules:

```text
- Keep security state separate from core identity fields.
- Lockout changes must create AuthEvent records.
- Password reset/temporary password actions must force password change.
```

### 9.3 `UserSession`

Purpose:

```text
Tracks issued refresh-token sessions and supports session review/revocation.
```

Recommended fields:

```text
id
user
refresh_token_jti           unique, indexed
device_label                blank text
device_fingerprint_hash     blank text
ip_address                  GenericIPAddressField nullable
user_agent_hash             hash only, never raw if avoidable
issued_at
last_seen_at
expires_at
revoked_at                  nullable datetime
revoked_reason              blank text/choice
is_active                   boolean
created_at
updated_at
```

Rules:

```text
- Never store raw refresh tokens.
- Store only token JTI or cryptographic hash where needed.
- Logout must revoke/blacklist refresh token where supported.
- Session list endpoints must not expose sensitive token material.
```

### 9.4 `AuthEvent`

Purpose:

```text
Append-friendly security event log for authentication activity.
```

Recommended fields:

```text
id
user                        nullable FK(User)
identifier_entered          blank; normalized or partially masked where appropriate
event_type                  enum
success                     boolean
failure_reason              enum/blank
ip_address                  GenericIPAddressField nullable
user_agent_hash             hash only, never raw if avoidable
request_id                  blank
metadata                    JSONField default=dict
created_at                  datetime
```

Rules:

```text
- AuthEvent must be append-friendly.
- Do not update/delete AuthEvent in normal application flows.
- Do not log passwords, JWTs, OTP codes, reset tokens, private keys, API keys, or Authorization headers.
- Internal failure reason may be specific, but public API response must remain generic.
```

Recommended event types:

```text

login_blocked_inactive
login_blocked_locked
```

## 11. Endpoint groups

All endpoints must use the standard API response envelope.
All endpoints must be documented in `authenticate/docs/API.md`.
All endpoints must be registered in the Core Policy Engine lifecycle.
All public endpoints must have throttling documented.
All protected endpoints must deny by default.

### 11.1 Public / unauthenticated authentication endpoints

These endpoints may be called without an existing authenticated session, but they must be heavily throttled and must not leak account existence.

| Method | Endpoint | Purpose | Policy key | Risk |
|---|---|---|---|---|
| `POST` | `/api/v1/auth/login/` | Login with username/password and possibly MFA | `authenticate.user.login` | high |
| `POST` | `/api/v1/auth/refresh/` | Rotate refresh token and issue new access token | `authenticate.session.refresh` | high |
| `POST` | `/api/v1/auth/logout/` | Revoke current refresh/session | `authenticate.session.logout` | medium |

### 11.2 Authenticated self-service endpoints

| Method | Endpoint | Purpose | Policy key | Risk |
|---|---|---|---|---|
| `GET` | `/api/v1/auth/me/` | Get current actor identity | `authenticate.user.read_self` | low |
| `PATCH` | `/api/v1/auth/me/` | Update limited self profile fields | `authenticate.user.update_self` | medium |
| `POST` | `/api/v1/auth/change-password/` | Change own password | `authenticate.user.change_password` | high |
| `GET` | `/api/v1/auth/sessions/` | List own active sessions | `authenticate.session.list_self` | medium |
| `POST` | `/api/v1/auth/sessions/<id>/revoke/` | Revoke one own session | `authenticate.session.revoke_self` | high |
| `POST` | `/api/v1/auth/sessions/revoke-all/` | Revoke all own sessions except optionally current | `authenticate.session.revoke_all_self` | high |

### 11.3 Staff/admin user-management endpoints

Until the dedicated permissions app exists, these endpoints must use the interim pattern:

```text
is_authenticated + is_staff
```

For the most dangerous endpoints, require:

```text
is_authenticated + is_superuser
```

| Method | Endpoint | Purpose | Policy key | Risk |
|---|---|---|---|---|
| `POST` | `/api/v1/auth/users/` | Create registered actor | `authenticate.user.create` | critical |
| `GET` | `/api/v1/auth/users/` | List registered actors | `authenticate.user.list` | high |
| `GET` | `/api/v1/auth/users/<id>/` | Read actor | `authenticate.user.read` | high |
| `PATCH` | `/api/v1/auth/users/<id>/` | Update actor identity/login flags | `authenticate.user.update` | critical |
| `POST` | `/api/v1/auth/users/<id>/enable-login/` | Allow actor to use software | `authenticate.user.enable_login` | critical |
| `POST` | `/api/v1/auth/users/<id>/disable-login/` | Prevent actor from logging in | `authenticate.user.disable_login` | critical |
| `POST` | `/api/v1/auth/users/<id>/lock/` | Lock actor account | `authenticate.user.lock` | critical |
| `POST` | `/api/v1/auth/users/<id>/unlock/` | Unlock actor account | `authenticate.user.unlock` | critical |
| `POST` | `/api/v1/auth/users/<id>/force-password-change/` | Require password reset on next login | `authenticate.user.force_password_change` | critical |
| `POST` | `/api/v1/auth/users/<id>/set-temporary-password/` | Staff sets temporary password | `authenticate.user.set_temporary_password` | critical |
| `GET` | `/api/v1/auth/users/<id>/sessions/` | Staff views actor sessions | `authenticate.session.list_for_user` | critical |
| `POST` | `/api/v1/auth/users/<id>/sessions/revoke-all/` | Staff revokes actor sessions | `authenticate.session.revoke_all_for_user` | critical |

MFA should be part of the serious authentication design. It may be implemented in the first version if approved, or staged as the immediate next hardening step.

| Method | Endpoint | Purpose | Policy key | Risk |
|---|---|---|---|---|
| `POST` | `/api/v1/auth/mfa/totp/setup/` | Begin TOTP setup | `authenticate.mfa.setup` | high |
| `POST` | `/api/v1/auth/mfa/totp/confirm/` | Confirm TOTP setup | `authenticate.mfa.confirm` | high |
| `POST` | `/api/v1/auth/mfa/totp/verify/` | Verify MFA challenge | `authenticate.mfa.verify` | high |

| `POST` | `/api/v1/auth/mfa/recovery-codes/regenerate/` | Regenerate recovery codes | `authenticate.mfa.regenerate_recovery_codes` | critical |

If MFA is not implemented in the first sprint, Claude must document it as a blocked/future hardening item, not silently ignore it.

## 12. Login flow

Login must follow this order:

```text
1. Normalize identifier.
2. Apply IP + identifier throttling.
3. Look up actor by username/email.
4. If not found, return generic public failure.
5. If actor exists but is_active=false, block with generic public failure.
6. If is_login_enabled=false, block with generic public failure.
7. If account_status is not active, block with generic public failure.
8. If locked_until is in the future, block with generic public failure.
9. Validate password using Django authentication/password hashers.
10. On invalid password:
    - record failed attempt
    - update UserSecurityState
    - allow django-axes to record/lock if installed
    - create AuthEvent
    - return generic public failure
11. On valid password:
    - reset failed_login_count
    - update last_successful_login_at
    - check password_change_required
    - check MFA requirement
    - issue tokens only after MFA succeeds when MFA is required
    - create UserSession
    - create AuthEvent
12. Return standard response envelope.
```

Public response must not reveal whether:

```text
the user exists
the password was wrong
the account is inactive
the login flag is disabled
the account is locked
MFA is enrolled for a specific account
```

Use a generic message such as:

```json
{
  "success": false,
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "Invalid credentials or account is not allowed to sign in.",
    "details": {}
  },
  "meta": {}
}
```

Internal `AuthEvent.failure_reason` may record the exact reason.

## 13. JWT and cookie strategy

Use SimpleJWT.

Recommended production strategy:

```text
access token lifetime: 5-10 minutes
refresh token lifetime: strict deployment 8-12 hours; normal deployment 1-7 days
refresh rotation: enabled
refresh blacklist after rotation: enabled
logout: blacklist refresh token and revoke UserSession
```

Browser storage strategy:

```text
refresh token: HttpOnly + Secure + SameSite cookie
access token: memory only, or HttpOnly cookie if CSRF strategy is properly implemented
```

Production cookie requirements:

```text
HttpOnly = true
Secure = true
SameSite = Lax or Strict
Path scoped as narrowly as practical
CSRF protection enabled for cookie-authenticated refresh/logout flows
```

Development may return tokens in response body for local testing, but this must be documented as development-only behavior.

## 14. Throttling and brute-force defense

Use layered protection:

```text
DRF throttling
django-axes if approved
failed_login_count in UserSecurityState
locked_until
AuthEvent logs
admin alert hook later
```

Recommended starting policy:

```text
5 failed attempts → temporary lock for 15 minutes
10 failed attempts within configured window → staff/admin review required
login endpoint throttle → strict per IP and per identifier
refresh endpoint throttle → strict per IP and per session/token family
MFA verify endpoint throttle → very strict
```

The exact numbers must be settings-driven, not hardcoded deep in services.

Document throttling in:

```text
authenticate/docs/API.md
authenticate/docs/SECURITY.md
settings documentation or comments
```

---

## 15. Password policy

Use Django password validators.

Recommended baseline:

```text
minimum length: 12
reject common passwords
reject numeric-only passwords
reject passwords similar to user attributes
password_change_required on first login
password_change_required after staff reset
temporary passwords expire
new password must not equal current password
```

Recommended future hardening:

```text
password history: block reuse of last 5 passwords
MFA mandatory for staff/admin users
MFA mandatory for high-risk organization roles later
admin alert on suspicious login patterns
```

Do not force global frequent password expiry unless the deployment policy explicitly requires it. Prefer risk-based password resets after compromise, staff reset, incident response, or sensitive role assignment.

Serializers own validation and input/output shaping.

Rules:

```text

- AuthEvent serializers must not expose sensitive metadata.
- Public login errors must be generic.
```
