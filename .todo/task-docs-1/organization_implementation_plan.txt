Organization App — Implementation Plan
Context
The user wants to build the `organization` Django app — the third governance-foundation module (after core.policy_engine and authenticate, both built), per .docs/mintflow_initial_architecture.md §9/§10.1/§27. It is the source of truth for organizational structure: organizations, internal unit hierarchy, positions, membership, position assignment, reporting lines, delegation, sites, and structural history. It owns structure only — no passwords, no RBAC/ABAC grants, no work/case ownership.

This is a Major scope task (schema change, new app, 12 models, migrations, services, selectors, ~50 API endpoints, management commands, tests, docs, policy metadata).

Prompted by: .docs/organization_prompt.md (derived from a 2,062-line draft, revised on two structural points before any code was written — see that doc's §3 and §10.12).

Architecture Decision
organization/ is a standard top-level Django app (not inside core/ — it is app-specific business logic, unlike the policy engine's approved core/ exception).

INSTALLED_APPS entry: "organization"
AppConfig: name = "organization", label = "organization"
Migration dir: organization/migrations/
URL prefix: /api/v1/organization/
Auth on views: IsAuthenticated (DRF default) + inline _require_staff() interim check (per CLAUDE.md §9, mirrors authenticate/views.py verbatim)
Hierarchy strategy: OrganizationUnit.parent (adjacency list) + OrganizationUnitClosure (closure table) — first use of a closure table in this codebase; existing hierarchies (PermissionCategory) use plain adjacency lists, insufficient at this app's stated scale (thousands of units per organization).
Organization itself is flat (no authority-bearing nesting) — see organization_prompt.md §3 for why the original "nested Organization" draft was rejected (it broke ReportingLine's same-organization rule for cross-org authority chains).

Step 6 — models.py
All 12 models inherit core.models.BaseModel except OrganizationEventLog, which additionally
defines a local AppendOnlyManager/AppendOnlyQuerySet (independent copy — see DATA_CONTRACT.md
"Deliberate deviations", matches the existing authenticate.AuthEvent /
core.policy_engine.PolicyChangeLog precedent of NOT sharing this pattern across apps).

Key constraints to get right:
- OrganizationMembership: UniqueConstraint(fields=["organization", "user"], condition=Q(ended_at__isnull=True))
  — NOT a hard unique_together (contradicts the ended_at/rejoin requirement).
- UnitMembership: UniqueConstraint(fields=["membership"], condition=Q(is_primary=True, status="active"))
- ReportingLine: UniqueConstraint(fields=["source_position"], condition=Q(is_primary=True, status="active", reporting_line_type="administrative"))
- PositionAssignment: UniqueConstraint(fields=["membership"], condition=Q(is_primary=True, status="active"))
- OrganizationUnitClosure: UniqueConstraint(fields=["organization", "ancestor", "descendant"]); CheckConstraint(depth__gte=0)
- OrganizationUnit: UniqueConstraint(fields=["organization", "code"])
- Position: UniqueConstraint(fields=["organization", "code"])
- OrganizationSite: UniqueConstraint(fields=["organization", "code"])
- Organization: code = CharField(unique=True) — globally unique, no tenant strategy exists yet.

Full field lists: organization_prompt.md §10.1–§10.12.
