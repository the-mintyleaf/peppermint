# Gaps & assumptions

What the backend docs do **not** answer. Each entry is a question for the backend
or an assumption the frontend is making — **ask, don't invent**. Nothing here may
be silently resolved in code without confirmation.

| #   | Gap                                                                                                                                                 | Impact on frontend                                                           | Assumption (if any)                                                                                    | Where the assumption lives           |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------ |
| 1   | Exact **401 / 403 response bodies** are not shown (only status codes and the standard envelope).                                                    | Can't type the auth-error body; rely on status code + the standard envelope. | Auth errors follow the standard `error` envelope; switch on HTTP status, not a specific code.          | api client 401 / 403 handling        |
| 2   | The **field-validation error body** for `reason > 1000 chars` (`error.details` shape, error code) is not enumerated.                                | Can't reliably map the `reason` field error to the form field.               | Treat `error.details` as opaque; fall back to `error.message`. Validate ≤1000 chars client-side first. | backup create form                   |
| 3   | The list has **no documented filter / search / ordering** query params (fixed newest-first order).                                                  | Can't offer server-side filtering by `status`, date range, or actor.         | List is newest-first only; do any filtering client-side over the fetched page.                         | backup list query                    |
| 4   | **Default page size** when `?page_size` is omitted is stated as 20 in this pack, but the DRF project default is not re-confirmed for this endpoint. | Prefetch counts / page size are a mild guess.                                | Assume 20 (max 100); always send an explicit `page_size`.                                              | list query params                    |
| 5   | `dump_format` is only ever `custom` today; whether other formats will ever be returned is unknown.                                                  | A single-value union may break if the backend adds formats.                  | Type it `"custom"` for now; widen the union if the backend adds values.                                | `enums.md` / `database-backup.md` §2 |
| 6   | No **retention / rotation, delete, or restore** endpoints exist — archives accumulate server-side.                                                  | The UI can't offer delete-old-backup or restore actions.                     | Don't build those controls; restore is a manual `pg_restore` operation.                                | operations backup UI                 |
| 7   | Behavior of a **stuck `in_progress`** row (from a crashed dump) — whether/how it is ever reconciled — is not specified.                             | Such a row shows as non-downloadable indefinitely.                           | Treat any non-`completed` row as not downloadable; surface `status` and don't offer download.          | `database-backup.md` §4              |

> When a gap is resolved (backend answers, or a new doc version lands), delete its
> row and fold the truth into the relevant file — don't leave stale assumptions.
